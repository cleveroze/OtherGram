# OtherGram — CLAUDE.md

OtherGram — форк Telegram для Android (upstream: DrKLO/Telegram) с премиальным
минималистичным ванильно-бежевым дизайном, глубокой кастомизацией интерфейса
и собственными функциями: кастомные бейджи, баннеры профилей и админ-панель.

- Репозиторий: https://github.com/cleveroze/OtherGram (ветка `master`)
- Upstream: https://github.com/DrKLO/Telegram
- Язык: Java (UI и логика), C/C++ (TMessagesProj/jni, нативные библиотеки)
- Сборка: Gradle, Android Studio, Android NDK

## Спецификация

**Главный источник требований — [OTHERGRAM_SPEC.md](OTHERGRAM_SPEC.md)** (полное ТЗ OtherGram 1.0).
Если этот файл расходится со спецификацией, приоритет у спецификации. Функции из ТЗ
нельзя сокращать или исключать по своему усмотрению.

## Цели версии 1.0

Всё перечисленное входит в **OtherGram 1.0**. Работу можно делить на этапы,
но ни одну функцию нельзя переносить за 1.0.

1. Тема **Vanilla Beige** и премиальный минималистичный дизайн.
2. Раздел **OtherGram Settings** с собственной иконкой: Appearance, Avatars,
   Typography, Chats, Navigation, Profile Customization.
3. Расширенная кастомизация: экспорт и импорт тем, пресеты, сброс, поиск по
   настройкам, мгновенный предпросмотр, раздельные настройки светлой и тёмной
   темы, отключение анимаций.
4. **Баннеры профилей**, видимые другим пользователям OtherGram.
5. **Кастомные бейджи** (Developer, Administrator, Tester, Contributor,
   Project Friend, Early Supporter, Custom) с информационным окном по нажатию.
6. **Админ-панель** с серверной проверкой прав по Telegram user ID.
7. **Серверная синхронизация** баннеров, бейджей, цветов имён и публичного
   оформления профиля. В официальном Telegram всё это не отображается.
8. Все основные функции Telegram сохранены.

## Правила разработки

### Общие
- Код и изменения на GitHub отправлять (`git push`, PR, релизы) только по
  явной просьбе владельца проекта.
- Работать в feature-ветках (`feature/<name>`), а не напрямую в `master`.
- Нельзя ломать и вырезать функции Telegram. Если изменение затрагивает
  существующее поведение, его нужно согласовать.
- Перед любым изменением, затрагивающим сборку, проверять, что проект собирается.

### Изоляция кода (для упрощения слияний с upstream)
- Весь новый код OtherGram держать в отдельном пакете
  `org.telegram.othergram` (подпакеты `settings`, `theme`, `ui`, `badges`,
  `banners`, `network`).
- В файлы Telegram вносить минимальные точечные вставки («хуки»), которые
  вызывают код OtherGram. Каждую вставку помечать комментарием `// OtherGram: <что и зачем>`.
- Новые ресурсы называть с префиксом `og_` (`og_ic_badge.xml`), строки — с префиксом `OG_`.
- **Строки интерфейса только в `res/values*/strings.xml`** (блок с комментарием OtherGram в конце файла).
  Тексты в приложение попадают через `TelegramStringsTask` (buildSrc), который читает только `strings.xml`;
  строки из других файлов показываются как `LOC_ERR:null`.
- Строки интерфейса выносить в ресурсы с локализацией: как минимум `ru` и `en`.
- Настройки OtherGram хранить в отдельных SharedPreferences (`othergram_config`),
  а не в настройках Telegram.

### Секреты и юридические требования
- `api_id` и `api_hash` получать на https://my.telegram.org для OtherGram.
  Ключи официального Telegram использовать нельзя.
- Не коммитить: `api_id`/`api_hash`, keystore, `google-services.json`,
  ключи и токены сервера. Брать их из `local.properties` или переменных
  окружения, файлы с секретами добавить в `.gitignore`.
- Соблюдать условия Telegram API: своё название и логотип, без слова
  «Telegram» в названии приложения, собственный `applicationId`, чтобы
  приложение ставилось рядом с официальным.
- Соблюдать GPL-2.0 (лицензию upstream): исходники OtherGram должны оставаться открытыми.

### Безопасность и приватность
- На сервер OtherGram никогда не отправлять сообщения, контакты, номера телефонов,
  содержимое чатов и сессионные ключи Telegram.
- Серверу передаются только Telegram `user_id` и данные, которые пользователь
  сам публикует в OtherGram: бейдж, баннер.
- Вся связь с сервером идёт только по HTTPS (TLS 1.2+) с certificate pinning в клиенте.

## Архитектура серверной части (бейджи, баннеры, админ-панель)

Telegram API не умеет хранить произвольные данные профиля, видимые только
форку, поэтому для OtherGram нужен собственный сервер **OtherGram Backend**.
Официальный Telegram к нему не обращается, поэтому бейджи и баннеры видны
только в OtherGram.

### Компоненты
- **API-сервер:** REST/JSON. Стек предстоит выбрать; рекомендация — Kotlin + Ktor
  или Go, база PostgreSQL, кэш Redis.
- **Хранилище медиа:** S3-совместимое, баннеры отдаются через CDN.
- **Бот верификации** `@OtherGramAuthBot`: подтверждает, что пользователь
  владеет Telegram-аккаунтом.
- **Админ-панель:** отдельное веб-приложение, работает только через API-сервер.
- Код сервера и админ-панели храним в отдельном репозитории, например
  `OtherGram-Backend`. Создавать его — только по решению владельца.

### Авторизация клиента (подтверждение владения user_id)
1. Клиент генерирует случайный `client_secret` и отправляет на сервер
   `hash(client_secret)`. Сервер выдаёт одноразовый `nonce` со сроком жизни 5 минут.
2. Клиент через свою MTProto-сессию отправляет боту `/start <nonce>`.
   Отправитель сообщения гарантирован Telegram, поэтому бот получает настоящий `from.id`.
3. Сервер связывает `nonce` и `user_id`.
4. Клиент предъявляет `nonce` и `client_secret` и получает токен доступа
   (короткоживущий) и refresh-токен. Перехват `nonce` без `client_secret` бесполезен.
5. Токены хранятся в клиенте в зашифрованном виде (Android Keystore).

### API (черновик)
- `GET  /v1/profiles?ids=1,2,3`: пакетно отдаёт бейджи и баннеры (публичное
  чтение с rate limit).
- `GET  /v1/me`, `PUT /v1/me/badge`, `POST /v1/me/banner`, `DELETE /v1/me/banner`.
- `GET  /v1/badges`: каталог доступных бейджей.
- `POST /v1/reports`: жалоба на баннер или бейдж.
- `/admin/v1/...`: только для ролей админ-панели.

### Синхронизация в клиенте
- Пакетные запросы (до 100 id), кэш в памяти и на диске с TTL (~1 час),
  инвалидация по `version`/`ETag`.
- Без сети показывать кэш. Если сервер недоступен, интерфейс Telegram должен
  работать как обычно, без ошибок.
- Не делать запрос на каждый открытый профиль: копить id и отправлять пачками.

### Защита сервера
- Rate limiting по IP и токену, валидация всех входных данных.
- Баннеры: лимит размера, проверка типа по содержимому, перекодирование на
  сервере (снятие EXIF и метаданных), премодерация или постмодерация.
- Не логировать пары «кто чей профиль запрашивал». Политика хранения логов — минимальная.
- Админ-панель: вход через Telegram-верификацию плюс allowlist администраторов,
  обязательная 2FA, роли (owner, admin, moderator), журнал аудита всех действий.
- Секреты только в переменных окружения или secret manager, регулярные бэкапы БД.

## Карта кода (Telegram 13.0.2, версия 7175)

Модули: `TMessagesProj` (весь код и ресурсы, Android-библиотека),
`TMessagesProj_App` (обычное приложение, `applicationId = APP_PACKAGE`),
`TMessagesProj_AppStandalone`, `TMessagesProj_AppHuawei`,
`TMessagesProj_AppHockeyApp`, `TMessagesProj_AppTests`. Основная разработка
ведётся в `TMessagesProj` и `TMessagesProj_App`.

### Как собирать
- Android Studio 2026.2, Gradle JDK 21 (`.gradle/config.properties`), SDK 36, NDK 27.2.12479018, CMake 3.22.1.
- В репозитории нет `gradlew.bat`, запуск через Git Bash:
  `JAVA_HOME=~/.jdks/jbr-21.0.11 ./gradlew :TMessagesProj_App:assembleAfatDebug -Pandroid.injected.build.abi=arm64-v8a -Pandroid.injected.testOnly=false`
  (параметр ABI собирает нативную часть только под arm64; первая сборка ~50 мин, повторные 1–2 мин).
  **`-Pandroid.injected.testOnly=false` обязателен**: без него в манифест попадает `testOnly=true`,
  и телефон отказывается ставить APK из файла («пакет недействителен»). Перед релизом проверять:
  `aapt2 dump xmltree --file AndroidManifest.xml app.apk | grep testOnly` — должно быть пусто.
- APK: `TMessagesProj_App/build/intermediates/apk/afat/debug/app.apk`, пакет `org.telegram.messenger.beta`.
